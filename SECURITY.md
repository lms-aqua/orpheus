# ORPHEUS — Security

This document describes what ORPHEUS actually does, and what it does not do.

It deliberately avoids "military grade", "unhackable", "zero trace", and
"completely secure". Those phrases have no defensible technical meaning, and
using them would misrepresent the protection a personal iOS app can offer.

> **Status:** this describes the implementation as it exists today. Sections
> marked *Not yet implemented* are design intent, not shipped behaviour. Nothing
> here should be read as a claim about code that is not written.

---

## 1. Threat model

### Protected against

| Threat | Mechanism |
|---|---|
| Someone with brief physical access to an unlocked device | App lock with biometric or passcode authentication, auto-lock timeout, privacy shield in the app switcher *(not yet implemented)* |
| Someone reading app files off a locked device | iOS Data Protection plus content encrypted at rest under a Keychain-held key |
| Someone extracting an unencrypted backup | Content blobs are ciphertext; the vault key is `ThisDeviceOnly` and does not migrate to a backup |
| Silent modification of stored content | AES-GCM authentication tags on every chunk; SHA-256 over ciphertext |
| Relocating ciphertext between items | Per-item HKDF key derivation, so ciphertext only opens in the slot it was written for |
| Truncating, reordering, or appending chunks | Chunk index and file header are authenticated as associated data |

### Not protected against

Stated plainly, because a security document that omits these is marketing.

- **A compromised device.** Malware with code execution, or a jailbroken OS, can
  read memory while the vault is unlocked. No app-level design prevents this.
- **A person who knows your passcode.** Device authentication is the trust root.
  Anyone who can unlock the device can unlock ORPHEUS.
- **Coercion.** ORPHEUS has no duress mode.
- **Content after it leaves.** Exported, shared, or copied content is outside
  ORPHEUS's control. Standard exports are plaintext by design — that is what
  makes them openable elsewhere.
- **Screenshots.** iOS provides no reliable way for an app to prevent a
  screenshot. ORPHEUS can *observe* capture state, and will, but it cannot block
  it and does not pretend otherwise.
- **Metadata at rest.** Entry titles, tags, timestamps, and Space names live in
  SwiftData as queryable values, not ciphertext, so search and sorting work
  without decrypting everything. Treat titles as less protected than bodies.
- **Traffic analysis or a hostile sync server**, once sync exists. The planned
  design encrypts before upload, but a server still observes item sizes and
  timing.

## 2. Encryption

**Cipher:** AES-256-GCM, via CryptoKit. No custom construction, and no
primitive Apple does not ship.

AES-GCM is authenticated encryption: it conceals content *and* detects
modification. A plain cipher without a tag would let an attacker flip bits in a
stored note undetected.

**Key hierarchy:**

```text
Vault master key  (256-bit, random, Keychain)
        │
        └── HKDF-SHA256(salt, info = purpose)
                │
                ├── entry payload key    (per entry UUID)
                ├── attachment key       (per attachment UUID)
                ├── thumbnail key        (per attachment UUID)
                └── archive manifest key
```

One master key with derived subkeys, rather than the master key used directly,
buys two things:

1. **Domain separation.** Ciphertext moved from one entry's slot to another
   fails to authenticate, so an attacker who can swap files cannot make entry A
   display entry B's contents.
2. **Nonce headroom.** AES-GCM's random-nonce safety margin applies per key.
   Per-item keys keep the message count under any single key small.

The HKDF salt is a fixed non-secret constant. That is appropriate here: the
input key material is already a full-entropy random key, and the per-item `info`
supplies the separation that matters. The salt and the purpose labels are part
of the on-disk format — changing either requires a format version bump and a
migration, never an edit in place.

**Nonces** are generated by CryptoKit per seal and stored in the sealed box.
Callers never choose one, which removes the possibility of reuse through
caller error.

## 3. Large files

CryptoKit's AES-GCM is one-shot: it wants the whole message in memory. Passing a
multi-gigabyte video through it would defeat the memory constraints this app is
supposed to respect.

Blobs are therefore split into 1 MiB plaintext chunks, each sealed
independently. Chunking naively introduces three attacks that whole-file AEAD
does not have, so each is closed:

| Attack | Defence |
|---|---|
| Reorder chunks | The chunk index is authenticated as associated data |
| Truncate the tail | `chunkCount` is in the header, and the header is authenticated in *every* chunk |
| Append extra chunks | Bytes after the declared final chunk are an error |

Format:

```text
offset  size  field
0       8     magic "ORPHBLB1"
8       2     version      (UInt16 big endian)
10      2     reserved     (must be 0)
12      4     chunkSize    (UInt32, plaintext bytes per chunk)
16      8     chunkCount   (UInt64)
24      ...   chunk frames

each frame:
  4 bytes  sealedLength (UInt32 big endian)
  n bytes  AES-GCM sealed box: 12-byte nonce ‖ ciphertext ‖ 16-byte tag
```

A declared chunk size above 64 MiB is rejected, so a corrupt or hostile header
cannot induce a huge allocation.

Peak memory stays around one chunk regardless of file size.

## 4. Key storage

The vault key is stored as a Keychain generic password item. It is never written
to `UserDefaults`, SwiftData, a plist, a log, or any file, and never appears in
source.

Accessibility is `ThisDeviceOnly`, so the key does not travel to iCloud Keychain
or into a device backup. A backup of an ORPHEUS install therefore contains
ciphertext that the backup alone cannot open — which is the intended property.

Where the device has a passcode set, the key item additionally carries an access
control requiring user presence, meaning the key itself cannot be read without
biometric or passcode authentication. Unlocking the vault *is* retrieving the
key; locking releases it. When no device passcode is set, that access control
cannot be applied, and ORPHEUS reports the weaker state accurately in Settings
rather than implying protection it does not have.

*The key-storage implementation and its in-memory test boundary are present in
the current working tree. CI compilation and real-device access-control
verification are still required before this section is considered shipped.*

## 5. Data at rest

- Metadata — titles, tags, timestamps, Space membership — is in SwiftData,
  unencrypted, so it can be searched and sorted. See the limitation above.
- Content payloads and attachments are encrypted blobs in app-controlled
  storage.
- The app requests `NSFileProtectionComplete` as its default data protection
  class. Individual blobs are created `completeUnlessOpen` where a long import
  must survive the screen locking partway through — an explicit, per-file
  decision, never a global downgrade.
- A failed decryption deletes its partially written output. Half-decrypted
  plaintext left on disk would be unencrypted user content that nothing owns.

### Sideloaded builds are weaker, specifically

Entitlements are applied when an app is signed, and the `.ipa` files distributed
for AltStore are **unsigned** so the owner's own Apple ID can sign them. A
sideloaded install therefore does not carry the app-wide
`NSFileProtectionComplete` default.

Content encryption is unaffected — `ChunkedCipher` sets each blob's protection
class explicitly rather than relying on the app-wide default — but the SwiftData
metadata store falls back to the system default class, readable after first
unlock rather than only while unlocked. Since metadata is already the weaker half
of this model, that is a narrowing of an existing limitation rather than a new
one, but it is a real difference from a properly signed build.

See [docs/SIDELOADING.md](docs/SIDELOADING.md) for the full comparison.

## 6. Verification

The test suite asserts security properties directly, not just round-trips:

- Ciphertext never contains its plaintext, including across chunk boundaries.
- Encrypting identical plaintext twice yields different ciphertext.
- Every single-byte mutation of a sealed box is detected — the test walks every
  offset.
- Cross-item and cross-vault decryption fail.
- Truncation, appending, chunk reordering, and header rewriting are each
  detected.
- A failed decrypt leaves no plaintext file behind.

Planned for the security review phase: confirming no plaintext reaches temporary
directories, that no key or entry body appears in logs, and that widgets and the
app switcher expose nothing sensitive.

## 7. Export

- **Standard export** produces plaintext — PDF, image, text — because the point
  is to open it elsewhere. The UI is explicit that exported content is no longer
  protected.
- **ORPHEUS archive** (`.orpheus`) is an encrypted portable container with a
  manifest, version, and checksums. Encrypted content is never silently
  downgraded to plaintext on export.

*Not yet implemented; specified for Phase 3.*

---

## 8. Sync

Not implemented. The intended design is CloudKit with client-side encryption, so
the server never holds plaintext or a key. Until it is built and tested, treat
ORPHEUS as local-only.

---

## 9. Export compliance

`ITSAppUsesNonExemptEncryption` is declared `false` in `Info.plist`, on the basis
that ORPHEUS uses only Apple's standard cryptography to protect the owner's own
data on their own device. This is the common reading of the exemption; confirm it
against current Apple guidance before any App Store submission. It is recorded
here so the declaration is a deliberate decision rather than a default nobody
examined.
